## 1. 通用生产设备模板

所有生产设备（精炼炉、粉碎机、配件机、研磨机、灌装机等）继承同一套规则，仅修改以下参数：

- **设备尺寸（footprint）**：占地的网格单元格数，如 `3x3`、`5x5`、`6x4` 等
- **生产配方**：设备可处理的配方列表，由 `recipe.csv` 定义
- **消耗时间**：每个配方的基准生产时间（秒）
- **槽位数量**：固体输入槽数 + 固体输出槽数（每槽一种物品，液体走专用 liquid 端口不占槽）
- **端口数量和位置**：输入端与输出端的数量及相对设备中心的偏移位置

## 2. 缓冲区系统

> **数据结构以 A3 §3 的 `BuildingComponent` 为准**。本节用"输入槽/输出槽"的概念描述行为规则，但实际存储是 `BuildingComponent` 的字段（`bufferInput` / `bufferOutput` 数组，每个元素是一个 `BufferSlot { itemId, count }`）。槽位数量由 `BuildingDefinition.inputSlotCount` / `outputSlotCount` 决定，每个槽的容量上限由 `BuildingDefinition.bufferCapacity`（默认 50）决定。

### 2.1 输入槽

输入槽对应 `BuildingComponent.bufferInput` 数组的一个元素 `BufferSlot { itemId, count }`，容量由 `bufferCapacity`（默认 50）限定。每个槽的锁定状态由其自身的 `itemId` 表示：`itemId === null` 表示该槽为空、未锁定；非 null 表示锁定该 itemId。

**规则**：

- 每个输入槽独立运作。槽为空时下一件物品决定其类型（`itemId` 设为该物品）
- 槽锁定期间只允许相同类型的物品进入（新物品 itemId 必须等于该槽 `itemId`）
- 不同类型的物品无法进入此槽，可尝试进入其他空输入槽；若所有输入槽都不接受，则停留在传送带上等待
- 当槽 `count` 降为 0 时解除锁定（`itemId` 置为 `null`）
- 下一件进入该槽的物品重新决定其类型

### 2.2 输出槽

输出槽对应 `BuildingComponent.bufferOutput` 数组，容量由 `bufferCapacity`（默认 50）限定。**输出槽一槽一物，与输入槽语义对称**——一个槽只容纳一种物品。当一个配方产出多种固体产物时，每种产物各占一个输出槽。

**规则**：

- 生产计时完成时，原子结算：扣输入槽原料 + 向输出槽加入产物（同一 Tick 内同时完成）
- 输出槽满时（某槽 `count` 达到 `bufferCapacity`）无法再加入该类产物 → 设备进入 `blocked` 状态
- `blocked` 状态下，即使生产计时已走完，结算也无法执行，原料**不会被扣除**，继续停留在输入槽中
- 产物类型与配方绑定，不受输入槽锁定限制
- 输出槽腾出空间后，设备尝试执行结算（扣输入 + 加输出）并恢复 `working`/`idle`

> **液体产物**：部分配方的产物是液体（如赤铜块的污水），液体走专用 `liquid` 端口，**不占固体输出槽**（液体系统 Phase 2+ 实现，详见 A3 §2 端口定义）。Phase 1 的设备只处理固体产物。

### 2.3 槽位数量

- **槽位数由设备配方决定**：固体输入槽数 = 该设备所有配方所需固体原料的最大种类数；固体输出槽数 = 固体产物的最大种类数。
- **精炼炉**：1 固体输入槽 + 1 固体输出槽（赤铜块的清水入/污水出走 liquid 端口，Phase 2）
- **粉碎机/配件机/塑形机/采种机**：1 进 1 出
- **种植机**：1 进 1 出（清水走 liquid 端口，Phase 2）
- **装备原件机/灌装机/封装机/研磨机/反应池/天有洪炉**：2 进 1 出
- 所有槽的容量上限统一为 **50**

## 3. 生产计时系统

> **本系统不存在"加工位"这一概念**（参照《明日方舟：终末地》游戏原版的生产逻辑）。生产过程只是一个**计时器**，计时器字段直接存储在 `BuildingComponent` 中，没有独立的接口或容器。

### 3.1 生产模型

生产的核心规则是：**生产期间原料始终停留在输入槽中，不会被扣除；只有当生产计时走完那一刻，才发生一次原子结算——同时扣除输入槽的原料、向输出槽加入产物。**

以精炼炉"晶体外壳"配方（`源矿×1 → 晶体外壳×1`，2 秒）为例，假设输入槽有 3 个源矿：

| 时刻 | 事件 | 输入槽(源矿) | 状态 |
|------|------|------------|------|
| T=0 | 检测到配方匹配 → 启动计时（**不扣原料**） | 3 | working，progress 从 0 开始 |
| T=0~2s | 计时推进，期间**原料始终是 3** | 3 | working，progress 0→1 |
| T=2s | 计时完成 → 原子结算：扣 1 源矿 + 加 1 晶体外壳 | **2** | idle（若无后续配方） |

计时字段（并入 `BuildingComponent`，无独立接口）：

```ts
// 这些字段直接定义在 BuildingComponent 中（见 A3 §3）
currentRecipeId: string | null;   // null = 空闲，无生产任务
progress: number;                 // 生产进度 0~1
elapsed: number;                  // 已消耗时间 (ms)
// totalTime 不存储在 Component，而是从 Recipe.time 读取
```

**规则**：

- 设备同一时间只有一个生产计时（单设备单计时器）
- **启动生产**：当输入槽满足某配方、且 `currentRecipeId === null`（空闲）时，启动计时——设置 `currentRecipeId`、`elapsed = 0`、`progress = 0`。**此时不扣除任何原料**。
- **计时推进**：每个 Simulation Tick (50ms) 中 `elapsed += 50ms`，`progress = elapsed / totalTime`（`totalTime` 取自 `Recipe.time`）。
- **计时完成（原子结算）**：当 `progress >= 1.0` 时，检查输出槽是否有空间：
  - 有空间 → **同时**扣输入槽原料（每个输入槽 count -= 需求量）、向输出槽加入产物（每个产物槽 count += 产出量），然后 `currentRecipeId = null`（清空计时）
  - 无空间 → 设备进入 `blocked` 状态，结算**暂不执行**，原料继续留在输入槽（未被扣除），等待输出槽腾出空间
- 结算完成、计时清空后，立即检测输入槽是否满足下一个配方。若满足则立即启动下一次计时；若不满足则设备进入 `idle` 状态。

### 3.2 计时完成条件

```
progress >= 1.0  →  等价于  elapsed >= totalTime
```

- 每个 Simulation Tick (50ms) 中 `elapsed += 50ms`
- `progress = elapsed / totalTime`
- 当 `progress >= 1.0` 时视为计时完成，执行原子结算（见 §3.1）

## 4. 端口轮询系统

### 4.1 输入轮询

精炼炉 3 个输入端口的连接顺序按 **"左 → 中 → 右"** 创建顺序排列。

**数据结构**：

```ts
interface InputPollState {
  ports: PortRef[];         // 按创建顺序排列的输入端口引用
  pollIndex: number;        // 当前轮询指针（0-based）
}
```

**输入轮询规则**：

- 维护一个轮询指针 `inputPollIndex`（`0 → 1 → 2 → 0 → ...`）
- 当存在可接受物品的输入槽（槽空可锁定新类型，或槽已锁定同类型且未满）时，按指针指向的端口尝试补货
- **补货成功**：对应输入槽 `count + 1`（槽空时设 itemId），指针移动到下一个
- **补货失败**（端口无物品 / 无可接受的槽）：跳过，指针移动到下一个
- 所有输入槽都满时，指针保持不动，不重置

**示例**：

```
初始指针: 0 (左)
左端口有物品且类型匹配 → 补货成功 → 指针移至 1
中端口无物品 → 跳过 → 指针移至 2
右端口有物品但类型不匹配 → 跳过 → 指针移至 0
...
```

### 4.2 输出轮询

精炼炉 3 个输出端口的连接顺序按 **"左 → 中 → 右"** 创建顺序排列。

**数据结构**：

```ts
interface OutputPollState {
  activePorts: PortRef[];       // 可正常输出的端口队列（按创建顺序）
  blockedPorts: PortRef[];      // 当前堵塞的端口
}
```

**输出轮询规则**：

- 维护输出端口列表，按创建顺序排列
- 当输出槽有物品时，按顺序尝试输出
- **输出成功**（物品进入传送带）：从列表移除 → 追加到队尾轮转
- **输出失败**（传送带堵塞）：跳过该端口，移动到下一个
- 堵塞端口不参与轮询，但保持引用
- 堵塞端口恢复时，追加到当前轮询队尾

**示例**：

```
初始顺序: [A, B, C]
A 成功 → [B, C, A]
B 堵塞 → [C, A]          (B 被移出 activePorts)
C 成功 → [A, C]          (C 移动到队尾)
B 恢复 → [A, C, B]       (B 追加到队尾)
```

## 5. 配方系统引用

### 5.1 配方数据结构

配方数据存储在 `doc/csv/recipe.csv`，结构如下：

```
物品名称,英文ID,类别,等级,合成设备,原料需求,消耗时常/秒,合成数量,描述,次要描述
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| 物品名称 | 产物的显示名称 |
| 英文ID | 产物的唯一标识符 |
| 类别 | 物品分类（如 AIC Products, Usable Items） |
| 等级 | 物品等级（1~4） |
| 合成设备 | 负责生产的设备名称（如精炼炉、粉碎机） |
| 原料需求 | 配方原料，多个原料用 `/` 分隔，格式：`原料名*数量` |
| 消耗时常/秒 | 生产耗时（秒） |
| 合成数量 | 单次产出的物品数量 |
| 描述 | 物品描述 |
| 次要描述 | 物品次要描述 |

### 5.2 配方数据模型

> **完整定义见 A4 §6.1**。此处为快速参考。

```ts
interface Recipe {
  id: string;                      // 唯一标识（同主产物可多配方，见 A4 §6.1 命名建议）
  outputs: RecipeOutput[];         // 产物列表（支持多产物/副产物，见 A4 §6.1.2）。outputs[0] 是主产物
  inputs: RecipeInput[];           // 原料需求（支持或/和，见 §5.3）
  equipmentId: string;             // 合成设备唯一 ID
  time: number;                    // 生产时间 (ms)
  level: number;                   // 物品等级
}

interface RecipeOutput {
  itemId: string;                  // 产物 ID
  count: number;                   // 产出数量
}

interface RecipeInput {
  alternatives: RecipeAtom[];      // 一组可选项，长度>1 表示"或"
}
interface RecipeAtom {
  kind: 'item' | 'tag';            // 具体物品 / 类别匹配
  ref: string;
  count: number;
}
```

### 5.3 原料匹配方式

支持三种匹配模式：

1. **具体物品**：`源矿*1` → 需要 1 个指定物品 `源矿`
2. **任意类别**：`（任意Plant类别的物品）*1` → 需要 1 个任意属于 `Plant` 类别的物品
3. **多选一（或）**：`源矿*1/晶体外壳粉末*1` → 1 个源矿**或** 1 个晶体外壳粉末都行

匹配时根据 `ItemDefinition.tags`（或 category）进行判定。

**或/和的解析规则**（对应 CSV 原料列的分隔符）：

- `+` 拆分为多个 `RecipeInput`（**和**关系，所有组都要满足）
- `/` 在同一 `RecipeInput` 内拆分为多个 `alternatives`（**或**关系，组内任选其一）

**示例配方（精炼炉）**：

| 产物 | 原料 | 时间 | 产出量 | 副产物 |
|------|------|------|-------|--------|
| 晶体外壳 | 源矿*1 / 晶体外壳粉末*1 | 2s | 1 | — |
| 蓝铁块 | 蓝铁矿*1 | 2s | 1 | — |
| 紫晶纤维 | 紫晶矿*1 | 2s | 1 | — |
| 赤铜块 | 赤铜矿*1 + 清水*1 | 2s | 1 | **污水*1**（液体，走 liquid 端口，Phase 2） |
| 碳块 | （任意Plant类别的物品）*1 | 2s | 1 | — |

> 注：recipe.csv 中原料需求字段使用 `/` 分隔多个原料，例如 `"源矿*1/晶体外壳粉末*1"` 表示该配方需要消耗 1 个源矿 **或** 1 个晶体外壳粉末（多选一）。多个不同类型的必要原料使用 `+` 表示，例如 `"赤铜矿*1+清水*1"` 表示同时需要 1 个赤铜矿 **和** 1 个清水。

### 5.4 生产触发

```
1. 当输入槽有物品且设备空闲（currentRecipeId === null）时，设备检查所有可用配方
2. 配方匹配条件：输入槽中所有原料需求都能满足
   - 具体物品匹配：某输入槽 itemId 匹配且 count ≥ 需求数量
   - 类别匹配：某输入槽物品符合该类别且 count ≥ 需求数量
3. 匹配到配方后（启动计时，不扣原料）：
   - 设置 currentRecipeId, progress=0, elapsed=0
   - 【注意】此时不扣除任何原料，原料继续停留在输入槽中
4. 计时完成后才发生扣除（见 §3.1 原子结算）：
   - 扣除输入槽对应数量的原料（每个槽 count -= 需求量）
   - 向输出槽加入对应数量的产物
   - 清空计时（currentRecipeId = null）
5. 未匹配到任何配方：
   - 物品继续保留在输入槽
   - 设备保持 idle 状态
```

## 6. 设备状态机

> **扩展（2026-08-17 已定案，T2.8 实现）**: 新增玩家手动暂停 **PAUSED**——设备弹窗"开/关"电源开关
> 写入 `BuildingComp.paused`（T2.8 先调试钩子 `__game.setPaused`，正式入口为 T2.15 设备弹窗，
> 样式复刻旧 Flutter 项目）。暂停时: 不推进计时、不吸入输入、不输出产物（物流视同离线）；
> 已走计时保留，恢复后从暂停处继续（冻结不归零）。PAUSED 与 IDLE/WORKING/BLOCKED 正交
> （叠加时优先显示暂停），NO_POWER 仍属 Phase 3+。状态外部视觉为顶层 LOGO 图标方案
> （正常=LOGO / 暂停=深灰图标 / 堵塞=红 X + 端口高亮），见 implementation-phase-2.md T2.8。

所有生产设备（精炼炉、粉碎机、配件机等）共用同一状态机：

```
                 ┌──────────────────────┐
                 │                      │
                 ▼                      │
  ┌──────┐  有匹配配方     ┌─────────┐  │
  │ IDLE │ ─────────────→ │ WORKING │  │
  │      │ ←───────────── │         │  │
  └──────┘  加工完成       └─────────┘  │
     ↑                        │         │
     │                    输出满?       │
     │                        │         │
     │                        ▼         │
     │                    ┌─────────┐   │
     └────────────────────│ BLOCKED │───┘
       输出有空间          └─────────┘
```

### 6.1 状态说明

| 状态 | 含义 | 行为 |
|------|------|------|
| **IDLE** | 空闲 | 等待输入槽出现物品。无生产计时（currentRecipeId = null），progress = 0 |
| **WORKING** | 正在生产 | 生产计时推进（progress 每 Tick 递增）。**原料仍在输入槽中未被扣除**。输入和输出物流继续运行 |
| **BLOCKED** | 输出阻塞 | 输出槽已满。若计时已完成，原子结算**暂不执行**（原料仍未扣，停留在输入槽）。输入物流不受影响（输入槽未满时可继续补货） |

### 6.2 状态转换条件

| 转换 | 条件 |
|------|------|
| IDLE → WORKING | 输入槽满足某配方条件，且无生产计时 → 启动计时（不扣原料） |
| WORKING → IDLE | 计时完成，原子结算成功（扣输入 + 加输出），且没有其他可匹配的配方 |
| WORKING → BLOCKED | 计时完成，但输出槽已满，结算无法完成 |
| BLOCKED → WORKING | 输出槽腾出空间，结算完成（扣输入 + 加输出），且输入槽仍满足配方 → 启动下一次计时 |
| BLOCKED → IDLE | 输出槽腾出空间，结算完成，且输入槽不满足任何配方 |

## 7. Tick 内执行顺序

每个 Simulation Tick (50ms) 中，生产设备的处理顺序如下（引用 A5 仿真规范及 DD-010）：

```
1. 更新设备内部状态
   1a. 若有生产计时：progress += 50ms（elapsed += 50ms）
   1b. 如果 progress >= totalTime → 计时完成
       - 检查输出槽是否有空间
       - 有空间 → 原子结算：扣输入槽原料 + 向输出槽加入产物（同一 Tick 内同时完成）
       - 无空间 → 进入 blocked 状态（不结算，原料继续留在输入槽）
       - 结算成功后清空计时（currentRecipeId = null）
   1c. 若计时已清空，尝试匹配新配方
       - 输入槽满足配方 → 启动新计时（不扣原料）

2. 处理输入物流
   2a. 检查输入端口 → 传送带有无物品传进来
   2b. 按输入轮询规则处理
   2c. 物品到达端口 center → 传入输入槽

3. 处理输出物流
   3a. 输出槽有物品 → 按输出轮询规则
   3b. 物品传入连接的下游传送带
```

### 7.1 执行优先级说明

- **设备内部状态更新优先于物流**：确保在当前 Tick 内已完成的结算能及时腾出输出槽空间，为后续生产留出容量
- **输入物流先于输出物流**：防止输入端口和新产出同时争抢输出槽导致逻辑帧时序混乱
- 这个顺序与 A5 / DD-010 中 `BeltSystem → MachineSystem` 的顺序一致（BeltSystem 负责物品在传送带上的移动，MachineSystem 负责设备内部状态和端口交互）

### 7.2 物品传入判定

物品从传送带传入生产设备时，需要根据传送带物品停止的位置来判断：

- 传送带上的物品会停在传送带的中心位置
- 物品走到输入端端口所在网格的中心后停止，才视为进入设备
- 当所有可接受该物品的输入槽都满了（达到 bufferCapacity 50）时，传送带物品无法进入设备，呈现堵塞现象，物品停留在前一格
- 当物品走到端口网格中心后消失（传入输入槽），后续物品继续向端口传输

## 8. 规则总结

| 规则 | 说明 |
|------|------|
| **槽位上限 50** | 所有设备的每个输入/输出槽容量默认 50 |
| **每槽独立锁定** | 每个输入槽独立锁定一种物品类型，槽空时解锁 |
| **生产期间不扣原料** | 原料在生产计时走完前始终停留在输入槽中，计时完成时才原子结算（扣输入 + 加输出） |
| **端口间互不干扰** | 输入端口之间独立，输出端口之间独立 |
| **轮询指针不重置** | 满载时不重置，从当前位置继续 |
| **堵塞端口跳过** | 堵塞不参与轮询，恢复后追加队尾 |
| **单设备单计时器** | 同一设备同一时间只有一个生产计时 |
| **设备优先于物流** | 先处理设备内部状态，再处理输入/输出（引用 DD-010） |
| **Definition 不引用 Entity** | 设备定义（配方、参数）是静态数据，不包含运行时引用（引用 DD-005） |
| **状态在 Component** | 设备运行时状态（计时、缓冲区内容）全部存储在 ECS Component 中（引用 DD-011） |
| **数据驱动** | 设备参数、配方数据由 CSV / Definition 驱动，不写硬编码类（引用 DD-003） |
