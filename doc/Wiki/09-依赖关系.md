```
  │     ├── game/world/OccupancyMap             ← MapInstance + data/buildings(effectiveFootprint)
  │     │                                          + components/BuildingComp(Direction)

  │     │                                          + BeltVectorGeometry(预览绘制)
  │     ├── game/systems/BeltSystem             ← belt/BeltPathGeometry(directionVector)
  │     │                                          + PortGeometry(inputPortCells, 堵塞分类用)
  │     └── game/systems/MachineSystem          ← machine/{ProductionOps,IntakeOps,OutputOps,
  │                                                BufferOps,DepotOps,PortStatusOps,LogisticsDebug}
  │
  ├── game/render/{SceneRenderer, Camera, CameraController, GridRenderer, AssetsLoader}
  ├── game/systems/{SelectionSystem, DeleteSystem}      SelectionSystem ← belt/{BeltSelection, BeltChainOps}
  ├── game/ui/{InventoryUI, DeviceReadout}              InventoryUI ← NineSliceAssembler + buildings
  ├── game/perf/PerfMonitor
  ├── game/data/{buildings, items, recipes}             buildings 零依赖；items/recipes 仅互依赖
  └── game/systems/belt/{BeltChainOps, BeltDockOps, BeltSelection}
```

分层方向（自上而下单向依赖，**底层不知道上层**）：

```
main.ts / Game.ts
    ↓
systems/*（游戏逻辑）
    ↓                        ↘
ECS.ts、world/*、data/*        render/*（渲染）
    ↓                            ↓
render/constants.ts（CELL_SIZE、SIM_STEP_MS 等基础常量）
```

一个值得注意的例外：`world/MapInstance` 与 `OccupancyMap` 依赖 `render/constants.ts`（CELL_SIZE）与 `data/buildings.ts`（effectiveFootprint）——constants.ts 实际是全项目基础常量层，不专属渲染。

### machine/ 子系统内部依赖

```
MachineSystem
  ├─ ProductionOps → BufferOps(consumeFromSlot)
  ├─ IntakeOps ───→ BufferOps(tryAcceptItem)、PortGeometry(重导出 inputPortCells)、
  │                 BeltSystem(STOP_MAX/PORT_ENTER_DONE 同源常量)、BeltPathGeometry(directionVector)
  ├─ OutputOps ───→ BufferOps、PortGeometry(rotatePort/portOutwardBase/rotateDirection)
  ├─ DepotOps ────→ IntakeOps(PORT_ENTER_PROGRESS、releaseArrivedItems 复用)
  ├─ PortGeometry（被 IntakeOps/OutputOps/BeltSystem/BeltCreationSystem 共用）
  ├─ PortStatusOps（IntakeOps + OutputOps 只读组合，被渲染与调试消费）
  └─ LogisticsDebug（单例，横切日志）
```

## 3. 关键依赖约束（违反会产生隐蔽 bug）

| # | 约束 | 原因 |
|---|---|---|
| 1 | **执行顺序**：GameLoop 中 `BeltSystem` 必须先于 `MachineSystem` 注册 | DD-010：物品先到端口（推进/钳制/放行），设备再结算/注入；顺序颠倒会有一 Tick 延迟抖动 |
| 2 | **常量同源**：`IntakeOps.PORT_ENTER_PROGRESS === BeltSystem.STOP_MAX(0.5)`、`PORT_RELEASE_PROGRESS === BeltSystem.PORT_ENTER_DONE(1.5)` | 吸入判定与推进钳制必须是同一坐标；两边各自定义会导致物品永远进不了门或穿透 |
| 3 | **几何单一事实源**：端口格几何只有 `PortGeometry`；旋转占地只有 `effectiveFootprint` | MachineSystem 吸入/出货、传送带吸附、堵塞分类、渲染高亮、占用表五处共用；任何一处另写公式就会"看着连上了实际不吸入" |
| 4 | **禁止成环**：`BeltSystem` 不得 import `machine/`（方向只能 IntakeOps → BeltSystem） | 若成环则端口几何无法共享——这正是 PortGeometry 从 BeltCreationSystem 下沉为独立模块的原因（T2.16） |
| 5 | **世界尺寸**：边界一律读 `MapInstance`，禁止新建全局 WORLD_* 常量 | 相机 clamp 与占用表边界同源（A11 WV-003，Phase 3a 无限世界铺路） |
| 6 | **SpriteComp.width/height 恒存 0° 尺寸**，旋转归渲染侧 | 与 `effectiveFootprint` 分工：逻辑用有效占地、渲染用未旋转尺寸 + 整体旋转 |
| 7 | **传送带落盘必须 `occupancy.occupy(gx, gy, 'transport_belt')`** | 设备与带的格位互斥完全由占用表中立，漏写会导致重叠放置 |
| 8 | **tickSimulation 先于 update（渲染）** | 渲染必须读完整 Tick 快照，不能读到半个 Tick 的中间态 |
| 9 | **改 BeltPathGeometry 三处联测** | "预览 ↔ 落盘 ↔ 渲染"共用同一套转角/旋转数学 |

## 5. 系统间解耦机制小结

| 机制 | 实例 |
|---|---|
| 构造函数回调注入 | RenderSystem ← 6 个读 BeltCreationSystem 状态的 lambda（Game.ts:56） |
| 共享状态对象 | `BeltSelection`（SelectionSystem 写、三个带渲染器读） |
| 共享判定函数 | PortGeometry / PortStatusOps / BeltDockOps（逻辑与渲染同口径） |
| 占用表中立 | PlacementSystem 与 BeltCreationSystem 零直接依赖，靠 OccupancyMap 互斥 |
| 每 Tick 重建索引 | `buildBeltCellIndex` / `collectInputPortCells`（MachineSystem 内，避免长生命周期缓存失效问题） |
