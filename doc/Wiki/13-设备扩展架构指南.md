# 13 · 设备扩展架构指南

> 上一篇：[12-文件清单](12-文件清单.md) ｜ 返回：[README](README.md)
>
> 定位：回答"未来设备变多、接口变杂，架构怎么演进"。基于 2026-09-05 的代码现状（Phase 2 收尾期）评估；标注"预判"的部分是建议而非既有代码。

## 1. 核心结论（TL;DR）

| 问题 | 答案 |
|---|---|
| 生产设备数量变多，要拆分吗？ | **不要**。数量增长由数据驱动模板吸收：加设备 = 1 条 Definition + SVG 资产 + CSV 配方，零代码（§2） |
| 设备**行为**出现新种类呢？ | 按 Depot 先例：判别字段 + 独立 ops 模块；第三个行为出现时再 Strategy 化（§3） |
| 出现新的**连接接口**（管道口、其他介质口）？ | 端口几何层完全复用；需实现"新介质四件套"：传输网络/推进系统/对接判定/状态判定（§4） |
| 现在就该动手的确定项？ | buildings.ts 按类别拆文件、端口模型二维化（direction × medium）——均已排期建议（§5） |

## 2. 加一台"同类"生产设备：零代码三步走

现有 6 台工具栏设备（精炼炉/粉碎机/配件机/采种机/仓库取货口/存货口）全部走同一条路径，第 7 台、第 50 台成本恒定：

| 步骤 | 做法 | 涉及代码 |
|---|---|---|
| ① 定义 | `data/buildings.ts` 加一条 `BuildingDefinition`：footprint、ports（input/output/liquid + 格偏移）、texture、inputSlotCount/outputSlotCount（=50 容量由 bufferCapacity 定） | 仅数据 |
| ② 视觉 | 设备 SVG 进 `src/assets/svg/`（w,h≥2 且标准端口布局 → `baseStyle:'nineslice'` 只画 equipment 专属层，底座零美术；1×n 或特殊外观走 whole 整图）→ `npm run pack-assets` | 仅资产；规范见仓库根 `doc/asset-drawing-standard.md` |
| ③ 配方 | `doc/csv/recipe.csv` 加行，设备列填与 `BuildingDefinition.name` 匹配的名字 | 仅数据 |
| （可选） | 上工具栏：加入 `TOOLBAR_BUILDINGS` 数组 | 仅数据 |

行为自动获得：idle/working/blocked 状态机、预约制吸入、输出轮询、端口高亮、配方匹配（按 CSV 序自动选第一条可满足配方）。

**验收**：`__game.placeAt(defId, gx, gy)` 程序化放置 + `__game.test('demoT25')` 风格一键链路测试；占位泄漏用 `__game.getOccupiedCells()`。

## 3. 行为扩展：判别字段 + ops 模块（Depot 先例）

### 3.1 先例解剖：仓库口是怎么接入的

仓库口是"第一种非通用生产行为"，它的接入方式就是未来所有新行为种类的模板：

1. `BuildingDefinition` 加判别字段：`depot: 'unload' | 'load'`；
2. 行为实现独立成 `systems/machine/DepotOps.ts`（58 行纯函数：无限源 `emitSourceToBelt` / 无限汇 `tryAbsorbHeadItemSink`）；
3. 编排器 `MachineSystem.update` 加一个早退分支：`def.depot !== undefined → updateDepot()`，且**复用** IntakeOps 的 `releaseArrivedItems` 与 0.5/1.5 节奏——物流纪律不因设备种类而变。

关键点：**MachineSystem 仍是唯一编排骨架**（遍历实体、固定三段顺序），新行为只增"分支 + 模块"，不动骨架。

### 3.2 预判会出现的新行为种类

| 行为 | 触发设备 | 打破的假设 | 预判接入方式 |
|---|---|---|---|
| 采集（无输入产出） | extraction 类矿机（A8 首批 15 台含采矿设备） | "必须先有输入带" | 新 ops 模块（如 `ExtractionOps`）：输入来自地图矿脉（`OccupancyMap`/矿点数据）而非传送带；输出复用 OutputOps |
| 多配方选择/并行 | 配件机类 + T2.15 弹窗 | `currentRecipeId` 单计时器假设 | 先支持"弹窗选定配方"（数据已就绪：`recipeIndex` 每设备是数组）；并行多计时器是真行为差异，届时再拆 |
| 断电 `no_power` | Phase 3c 电力系统 | "设备恒有电" | 状态机加一态 + PowerSystem 插入 Tick 第 0 位（A5 已预留顺序位）；paused 的"物流视同离线"语义可复用 |
| 多阶段加工/中间缓存 | 远期 | "一段式计时" | 这是真正的 Strategy 化触发器 |

### 3.3 Strategy 化的时机与形态（预判）

**时机**：第三个行为种类落地时（现在只有"通用生产"与"Depot"两种，if-else 尚可）。

**形态**（保持 DD-010 顺序与公共物流不动）：

```ts
// 预判草图——现在不要实现
interface DeviceBehavior {
  /** 每 Tick 被编排器调用一次；返回是否需要后续输入/输出物流环节 */
  update(ctx: BehaviorContext, comp: BuildingComp, def: BuildingDefinition): void;
}
// ProductionBehavior（现 updateInternal+absorb+emit 骨架）
// DepotBehavior（现 updateDepot）
// ExtractionBehavior（未来）
// BuildingDefinition 增加 behavior 判别字段，MachineSystem 据此分发
```

编排器保留：遍历 `world.query('BuildingComp')` → paused 检查 → 按 behavior 分发。吸入/输出物流原语（IntakeOps/OutputOps）作为公共设施继续被各 behavior 复用。

### 3.4 反模式（明确不做）

- ❌ 每种设备一个类（`class Furnace`）——违背 DD-003/005 数据驱动，组合爆炸；
- ❌ 每类设备一个 System 注册 GameLoop——破坏 DD-010 顺序保证，公共物流逻辑重复；
- ❌ 只有两种行为时就抽象 Strategy——过早；Depot 的 if-分支完全够用；
- ❌ 新行为自带一套 0.5/1.5 节奏或连接判定——必须复用 IntakeOps/OutputOps 常量与函数（见 §4.4 纪律）。

## 4. 连接接口扩展：新介质接入框架

未来设备会有传送带口之外的接口——**管道口**（Phase 3b，液体/气体）、以及更远期的其他传输介质。本节给出通用的接入框架。

### 4.1 先看清现状：一个"接口"其实是三件独立的事

以现有的传送带固体口为例，它的"连接"由三个正交层组成：

| 层 | 承担的事 | 现有代码 | 与介质的关系 |
|---|---|---|---|
| **几何层** | 端口在哪格、朝哪边 | `PortGeometry`（rotatePort / portOutwardBase / rotateDirection） | **介质无关**——液体口、管道口可直接复用 |
| **介质协议层** | 怎么判定"连上了"、怎么传输 | 固体：`IntakeOps.findFeederBelt`（朝向侧供给格 + 逆朝向段）+ 预约制两阶段（0.5/1.5）；`OutputOps.findReceiverBelt` + 空段注入 | **每种介质一套** |
| **视觉层** | 端口面板/箭头/设备外观 | `PortMask.portMaskFromDef`（从 ports 派生切片）+ `PortHighlightRenderer`（连接黄/堵塞红） | 半通用——切片素材按介质分 |

另一侧的传输网络也是介质专属：固体 = 传送带（`BeltSegmentComp` 实体 + `BeltSystem` 推进）；液体/气体 = 管道（Phase 3b，A9 预告"同拓扑不同参数：2.0 格/秒、容量 4"，即很可能复用传送带的段实体+推进系统骨架，只换参数与原语）。

### 4.2 端口模型二维化（已知欠债，新接口的先决条件）

当前 `Port.type = 'input' | 'output' | 'liquid'` 是**单轴**——"液体"和"方向"耦合在一个枚举里（'liquid' 表达不了"液体入"还是"液体出"，靠 `dx===0 / dx===w-1` 左右约定补）。接多种介质前应拆成二维：

```ts
// 预判目标模型（触发时机见 §5）
interface Port {
  medium: 'solid' | 'liquid' | 'gas';   // 介质
  direction: 'in' | 'out';              // 方向
  position: { dx: number; dy: number };
  itemFilter?: string[];                // 已预留（物品准入口 Item_Control_Port 用）
}
```

迁移影响面：`PortGeometry`（按 medium+direction 过滤）、`PortMask.portMaskFromDef`（补 top/bottom.liquid 分支，S3 文档已预留此扩展点）、`PortStatusOps`、设备 SVG 层命名。拼装管线、烘焙缓存、Definition 结构本身零改动。**迁移策略**：新旧字段并存读取（`type` 作为 `medium×direction` 的派生兼容层），存量 15 条定义逐条换。

### 4.3 新介质四件套（以管道为例的接入清单）

给设备接一种新传输介质，需要实现四个新件 + 三处复用：

| # | 新件 | 管道口的具体形态（预判） |
|---|---|---|
| 1 | **传输段实体**（BeltSegmentComp 等价物） | 管道段：1×1 Cell + `PipeSegmentComp`（介质容量 4 而非一格一物品；A9：与传送带同拓扑） |
| 2 | **推进系统**（BeltSystem 等价物） | `PipeSystem`：每 Tick 推进流体；注册在 MachineSystem 之前（同 DD-010 顺序理由） |
| 3 | **对接判定**（findFeeder/Receiver 等价物） | `PipeOps.findFeederPipe / findReceiverPipe`——几何口径与固体完全一致（朝向侧供给格 + 逆朝向段），只换段组件类型 |
| 4 | **吞吐原语**（Intake/Output 等价物） | 管道版预约制：容量 4 的"预约多个 fluid 单位"，进度语义从"格内位置"改为"管内容量占比" |

| 复用 | 说明 |
|---|---|
| `PortGeometry` 几何层 | 直接复用，介质无关 |
| `PortStatusOps` / `PortHighlightRenderer` | 扩展 medium 维度，颜色语义沿用（连接/堵塞） |
| 创建交互模式 | 传送带的"端口起点 + 寻路预览 + 终点吸附"（E 模式）可整体克隆为管道铺设模式（A12 §18 已注明轨道铺设也复用此交互） |

**传送带侧的例外要记住**：传送带本身没有显式 Port（A3：靠方向+相邻隐式判定）；`Belt_Bridge` 是唯一允许与传送带共格的设备（防穿模例外，A9）。新介质若出现同类"跨接"设备，沿用"Definition 特殊标记 + 占用表特判"的方式，不要开放通用共格。

### 4.4 纪律：所有介质必须同一套口径

这些约束是固体口踩过的坑换来的（见 [09-依赖关系](09-依赖关系.md) 约束表），新介质照办：

1. 连接判定只有一份实现，供 **创建吸附 / 运行吸入 / 堵塞分类 / 渲染高亮** 四处共用——禁止各写各的（否则"看着连上了却不通"）；
2. 门口节奏常量（现 `STOP_MAX=0.5 / PORT_ENTER_DONE=1.5`）跨系统**同源引用**，禁止复制数值；
3. 端口几何只认 `PortGeometry`，传输占地只认 `effectiveFootprint`；
4. 新介质的 Ops 与 BeltSystem 之间禁止反向 import（PortGeometry 下沉模式）。

## 5. 确定要做的规模拆分（排期建议）

| 项 | 触发条件 | 动作 | 代价 |
|---|---|---|---|
| `data/buildings.ts` 拆文件 | 设备定义超过 ~30 条 / 文件接近千行 | 按 category 拆 `data/buildings/{production,logistics,agriculture,defense}.ts`，入口聚合导出；`TOOLBAR_BUILDINGS` 留在入口 | 纯文件搬移，零语义变化 |
| 端口模型二维化（§4.2） | 第一台**顶/底边液体口**设备设计时；或管道介质开工时 | 按 §4.2 迁移 | 中等，涉及 PortGeometry/PortMask/PortStatusOps/存量定义 |
| T2.15 弹窗 definition 驱动 | T2.15 开工时 | 面板内容（配方列表/开关/进度）由 Definition（或其 UI 扩展字段）驱动，禁止弹窗内硬编码设备 id | 小 |
| 仿真休眠/脏列表 | 千台级设备且 profiling 显示 MachineSystem 为热点 | 空闲设备（无物品到门口+无计时+输出空）跳过；传送带格索引改增量维护 | 中等，先测量再动手 |

## 6. "我要加一台设备"决策检查清单

```
新设备需求
  ├─ 行为与现有通用生产一致？
  │    ├─ 是 → §2 三步走（Definition + SVG + CSV），零代码 ✅
  │    └─ 否（采集/多计时/断电…）→ §3：判别字段 + 新 ops 模块 + MachineSystem 分支；
  │         若是第三种行为 → 同步做 Strategy 化
  ├─ 需要新的连接接口（管道/气体/其他）？
  │    └─ 是 → §4：介质四件套 + 端口模型先二维化 + 几何层直接复用
  ├─ 特殊占地/共格需求（如物流桥跨带）？
  │    └─ Definition 特殊标记 + OccupancyMap 特判，不开通用口子
  └─ 只是外观不同（皮肤/尺寸）？
       └─ 纯 §2，注意 w,h≥2 走 nineslice、1×n 走 whole
```
